Step 0

登入測試帳號

運作腳本永遠以使用者操作為起點，測試頁面比照正式 App 走登入取得 Token，而非直接夾帶帳密呼叫其他 API。

起點

使用者坐上椅子（Check-in）

運作腳本一的操作起點：「使用者坐上椅子後系統自動監控」。呼叫 POST /api/chair/checkin 讓登入帳號成為目前椅子感測資料的歸屬對象， 之後的感測數據與通知才會正確算在這個帳號名下（避免椅子先前被其他測試帳號 check-in，導致下面查不到自己的通知）。

A.0 ～ A.4

感測數值 → 系統自動預測坐姿並儲存

A.0 讀取壓力感測器數值 → A.1 發布坐姿資料 → A.2 轉送坐姿資料（正式環境經 EMQX MQTT Broker pub/sub，由 mqtt_subscriber.py 訂閱）→ A.3 分析坐姿類別 → A.4 儲存坐姿紀錄。 本頁以 POST /api/posture 模擬 ESP32 送出的感測數值，直接觸發後端相同的預測與寫入邏輯（跳過 MQTT 傳輸層，僅為測試頁面簡化，正式管線仍走 MQTT）。

A.5

系統自動建立坐姿提醒通知

查詢 GET /api/notification/history 最新一筆，確認上一步驟非標準坐姿時是否自動建立通知。

A.6 ～ A.9

觸發馬達決策 → 記錄 → 發布馬達指令

A.6 觸發馬達決策 → A.7 紀錄馬達觸發（寫入 MotorLog）→ A.8 發布馬達指令 → A.9 轉送馬達指令（經 MQTT Broker 送往 ESP32，Topic：chair/vibration/01/cmd）。 呼叫 POST /api/motor/trigger，依上方最後偵測到的坐姿決定觸發哪幾顆馬達（M1～M4，對應電路設計編號）。

A.10 ～ A.11

馬達實際震動 ＋ App 推播提醒

A.10 執行馬達震動、A.11 推播提醒通知為硬體端／App 端的實際動作，需搭配實體 ESP32 與 App 展示，不在本測試頁面涵蓋範圍內。 本頁僅涵蓋軟體端 A.0～A.9：MQTT 指令是否成功發布可由上方「mqtt_published」欄位確認；實際馬達是否震動、App 是否收到推播需另外錄製硬體 Demo 影片佐證。
