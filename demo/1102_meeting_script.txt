【Page 6：系統三層架構：即時在椅子、分析在雲端】
────────────────────────────────────────
先用架構圖說明這次改了哪裡，後面各頁依研究進度表的順序報告。

系統依處理時間分成三層。第一層是邊緣層，也就是椅子上的 ESP32，時間等級
是毫秒到秒，負責用重心判斷坐姿、壞坐姿時自動震動，這一層斷網也能運作。
第二層是雲端辨識層，時間等級是秒，後端用 AI 坐姿模型判斷坐姿並寫入紀錄；
這次新增了多張椅子、個人校正、自動離座。第三層是代理層，也就是 Physio
Agent，在使用者詢問或每週報告時才執行，用 LLM 加 MCP 加 ReAct 分析長期
趨勢、給個人化伸展建議；這次改成非同步任務，並做了防幻覺評測。

椅子和後端之間用 MQTT，每張椅子有自己的頻道；網頁版和 iOS 透過 HTTP API
存取雲端，用 Token 識別使用者。紅色標籤是這次新增的部分，橘色是規格已經
交給硬體、等待實作的部分。

【Page 7：Physio Agent 防幻覺評測：方法】
────────────────────────────────────────
這頁對應進度表「建立 Agent 防幻覺量化評測機制」的前兩項：建立標準測試
問題集、撰寫自動化評測腳本。

題目和標準答案都是對照知識庫人工標註的。LLM 輸出有隨機性，所以每題重複
3 次，取平均和標準差。題庫 36 題分四類：坐姿建議、人體工學、應該拒答的
範圍外問題，例如止痛藥、診斷、懷孕，以及故意誘導 AI 捏造的題目。另外有
10 題驗證題，是調整完才建立、從來沒有拿來調整過的，用來確認改善不是只
適合原本的題目。

五項指標：引用正確率、關鍵內容命中率、拒答正確率、誤拒率、幻覺率。幻覺
除了比對禁止詞，還有「數字無出處檢查」：回覆裡每個數字都必須出現在
Agent 這次實際查到的文獻中，否則就算捏造。

【Page 8：Physio Agent 防幻覺評測：結果】
────────────────────────────────────────
這頁對應進度表「防幻覺驗證收尾與優化」：原本排在 11/10 到 11/16 的 KPI
定稿和依結果調整 Prompt，已經提前完成。

改善後拒答正確率從 12.5% 提升到 100%，幻覺率從 2.8% 降到 0，關鍵內容命中
率從 81.4% 到 93%，誤拒率維持 0。從未用於調整的驗證題，拒答正確率也從
0 提升到 83.3%。

評測找出兩個真實問題。第一，該拒答的幾乎都沒拒答，問止痛藥、懷孕時 AI
會跳過問題改給坐姿建議；修正方式是在 Prompt 加入 Step 0 範疇判斷。
第二，右傾查到左傾的文獻，因為中文向量分不出左右，伸展方向相反會給錯
建議；修正方式是改成關鍵字導向加語意檢索。兩個都已經修正並部署。

也說明過程：第一版 Step 0 太嚴格，誤拒率衝到 42%，連「座深怎麼調」都
拒答，改成明確列出可回答範疇才平衡。引用率從 94 降到 91.7，是因為兩題
誘導題改成保守拒答，安全但沒有引用文獻。仍待改善的是飲食類拒答不穩定，
已經排進 11/10 之後的進度。

────────────────────────────────────────
【Page 9：AI 建議改為非同步任務】
────────────────────────────────────────
接下來三頁對應進度表「後端非同步化與承載驗證」。

原本 AI 建議是同步的：App 送出後要等 OpenAI 回應 6 到 25 秒，這段時間佔住
伺服器一條執行緒，最多只能同時服務 24 人。

改成非同步之後，流程是：App 送出 POST /agent/jobs，Gunicorn 只在資料庫
建立一筆任務，馬上回 202 和任務編號；另外有一個 agent-worker 服務，用
async/await 的 event loop 從資料庫領任務，去呼叫 MCP 和 OpenAI，等待
OpenAI 的時候不佔執行緒，可以同時處理很多筆。App 每 2 秒查一次任務狀態，
完成時拿到建議，格式跟舊版相同。

三個重點：伺服器不會被卡住；每筆任務最多 60 秒，逾時會標記失敗並附中文
原因；要提高處理量只要多開幾個 worker，領任務用 SKIP LOCKED，不會兩個
worker 搶到同一筆。

────────────────────────────────────────
【Page 10：測試結果：1000 人同時問 AI】
────────────────────────────────────────
測試方法：1000 個虛擬使用者在同一瞬間送出請求。為了不產生 OpenAI 費用，
AI 回應時間固定模擬成 10 秒，以 App 的 90 秒逾時當上限。

同步版本 90 秒內只完成 193 人，19.3%；非同步版本 1000 人全部完成，最慢
20.7 秒。原因是同步時伺服器同時只能處理 24 人，每人佔 10 秒，90 秒內
理論上最多約 216 人；非同步時送出任務平均 542 毫秒就回應，1000 筆同時在
worker 裡等待。

限制是：真實情況下瓶頸會變成 OpenAI 的速率上限，而不是我們的伺服器。

【Page 11：延遲與併發測試（含統計值）】
────────────────────────────────────────
每項測試都附上方法和統計值。上面是延遲測試，每支 API 用單一連線
循序打 100 次，列出請求和回應的封包大小，以及平均、標準差、最小、最大。
坐姿預測 POST /posture 平均 56 毫秒，因為要跑 AI 模型推論。

下面是併發測試，針對坐姿預測，1、10、30、50 人同時持續送 15 秒，錯誤率
都是 0。每秒能處理的量在 90 筆左右就到頂了。

這也說明為什麼要降低推論頻率：如果椅子每 0.5 秒傳一筆，只撐得住約 45
張椅子；改成有變動才傳、加上每 5 秒同步一次，大約可以撐 450 張。

【Page 12：震動提醒與分工：即時交給椅子】
────────────────────────────────────────
這頁對應進度表「邊緣端即時提醒與斷網容錯」。

即時的部分全部交給椅子：壞坐姿震動、久坐提醒、LED 燈條，斷網都能照常
運作；後端負責坐姿紀錄、AI 分析和通知 App。

過程中發現一個問題：原本椅子和後端都會在壞坐姿時發震動指令，造成重複
震動，而且後端的馬達編號跟椅子實際的編號不一樣，四種坐姿全部震錯
馬達。處理方式是後端不再自動發震動，即時提醒交給椅子，也符合斷網仍能
提示的要求；手動觸發的對應表改成實際位置。

────────────────────────────────────────
【Page 13：多張椅子：量產架構（已上線）】
────────────────────────────────────────
接下來五頁對應進度表「多椅量產架構與個人化校正」。

每張椅子用 ESP32 的網卡位址產生編號，量產時燒同一份韌體就好。每張椅子的
資料送到自己的頻道，後端第一次收到資料就自動登記這張椅子，再依椅子找出
目前坐的人，資料寫進那個人的紀錄，馬達指令也只送到那張椅子。

入座規則是一張椅子一人、一人一張椅子，換椅子時原本的入座會自動結束。
另外新增自動離座：椅子連續 10 分鐘沒人或離線就自動離座並通知，避免
下一位坐上來的資料記到前一位名下。舊的 App 和舊韌體不用改也能照常運作。

────────────────────────────────────────
【Page 14：個人化校正：校正一次，換椅子也通用】
────────────────────────────────────────
每個人體型不同，坐正時的重心也不同，所以加入個人校正。使用者在 App 按
校正，椅子取樣 5 秒算出坐正時的重心，結果存在使用者身上，之後坐任何一張
椅子都會自動送過去，不用重新校正。椅子 10 秒沒回應時改由後端用資料計算；
校正時坐不穩會請使用者重來。

沒校正的人用預設中立點，優先順序是：個人校正、這張椅子的平均、全部
椅子的平均、最後才是韌體內建的幾何中心。預設值由後端保管、每週重新
計算，調整時不用重燒韌體。

為什麼不直接用幾何中心？正式資料 2,151 筆正常坐姿的平均重心，比幾何
中心往後 0.036，約綠環半徑的一半。用幾何中心的話，正常坐著也容易被判成
後仰而被震，所以預設值改用真實資料計算。

【Page 15–17：展示：多張椅子＋個人校正】
────────────────────────────────────────
實體椅子目前離線，所以用程式模擬兩張新韌體的椅子，後端是跟正式環境同一份
程式。截圖依步驟編號，右邊是每一步的重點。

第 15 頁：[1] Alice 坐 A 椅、Bob 坐 D 椅，兩人都還沒校正，入座回應的

設定裡沒有帳號名稱。[2] Alice 按校正，後端馬上回 202，App 每秒查一次；
椅子取樣 5 秒後回報成功，method 是 device，A 椅接著收到她的個人中立點。

第 16 頁：[3] Bob 第一次校正時身體有移動，椅子回報失敗，App 顯示中文原因，
請他坐正再試。[4] 第二次模擬椅子沒有回應，例如舊韌體，可以看到後端從第 1
秒等到第 10 秒，然後改用最近收到的資料自己計算，method 是 backend。

第 17 頁：[5] 兩張椅子同時送資料，Alice 左傾、Bob 頭部前傾，兩人的紀錄各自

不用重新校正，G 椅自動收到她的中立點，A 椅恢復預設值。17 項檢查全部通過。
自動離座要等 10 分鐘，沒有在這裡展示，已經用整合測試以模擬時間驗證。

【Page 18：健康介入功能後端支援：AI 每日任務】
────────────────────────────────────────
這頁對應進度表「健康介入功能後端支援」。

App 的健康花園原本是前端寫死的 6 個任務，每個人都一樣。現在改由後端依
每個人近 7 天的坐姿產生，每人每天 3 個任務，當天固定不變。

流程是：先統計近 7 天的壞坐姿，從知識庫 18 個核查過的伸展動作中列出候選，
排除最近一次 AI 建議的同類動作和昨天做過的動作；再請 LLM 挑 3 個、依使用
者的坐姿寫個人化說明。LLM 的輸出會再檢查：動作必須在候選內、類別不能
重複、說明不能有網址，影片連結一律從知識庫帶入，避免 AI 捏造連結。

AI 失敗時改用坐姿頻率查表，資料不足時給通用的安全動作，所以不會空掉。
跟 AI 建議去重是看「動作類別」，例如胸部擴展和胸椎伸展名稱不同但都是
開胸，也算重複。另外新增完成紀錄的 API，記錄使用者做了哪些動作和回饋，
下次挑選時會參考；也完成了前端要求的頭像上傳。測試 24 項全部通過，
已經部署，網頁版實測正常。

【Page 19–20：後端 API 端點總表】
────────────────────────────────────────
這兩頁和下一頁對應進度表「整理後端 API 文件，支援 Android 對接」，
目前進行中。

後端全部 30 支 API，依功能分成帳號、坐姿、AI 建議、健康介入、座椅、
提醒、系統。每支都標出方法、網址、需不需要登入、由誰呼叫。使用者是用
Token 識別：登入後拿到 Token，之後每次請求放在 Authorization 標頭，所以
網址裡不會出現 user ID，使用者也沒辦法改網址去看別人的資料。

紅字是這段期間新增的：非同步 AI 任務的送出和查詢、列出所有椅子、個人
校正、頭像上傳、伸展完成紀錄。最下面是 MQTT 頻道，每張椅子在自己的
chair/{id} 底下，分成感測資料、中立點設定、校正指令、椅子回報。

【Page 21：前端串接與欄位核對】
────────────────────────────────────────
這頁對應進度表「核對現有前端呼叫欄位／回應格式落差」，原本排在 11/21，
已經提前開始。

前端有網頁版和 iOS 兩份程式，我逐一核對它們呼叫的欄位和後端實際的回應
格式，找出的落差整理在這頁。例如通知頁呼叫了給椅子用的 pending API，
呼叫一次就會被標成已送出，第二次就拿不到；/me 的回應被當成包在 user 裡，
所以顯示 null；授權標頭用了 Bearer，後端只接受 Token。這些都已經寫進
串接文件，通知頁還等前端修改。頭像上傳和健康花園任務則是由後端新增功能
處理，已經完成。

文件目前是人工整理、每一支都實際打 API 驗證；之後依進度改成自動產生。

【Page 22：下一步】

後端：硬體上線後接上新頻道實測、前端改版後移除舊 API、改善飲食類拒答與
