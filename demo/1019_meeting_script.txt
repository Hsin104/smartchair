接下來報告物理治療師 Agent 這部分的進度，這週主要是兩件事：第一，把後端
從 Django 內建的開發用伺服器，換成正式環境用的 Gunicorn，並且用壓力測試

────────────────────────────────────────
【Page 22：正式部署：runserver → Gunicorn】
────────────────────────────────────────
原本後端是用 Django 內建的 runserver 在跑，它是開發用的伺服器，只有單一
process。我們的坐姿預測要跑 TensorFlow 推論，受到 Python GIL 的限制，
單一 process 沒辦法同時用到多個 CPU 核心，人一多就只能排隊。

上面這條是請求的完整路徑：使用者手機或椅子的 ESP32 送出請求，經過 ngrok
做 HTTPS 對外轉發，進到 Gunicorn 的 master，由 master 分派給 3 個
worker，worker 再去存取 PostgreSQL 資料庫，或是呼叫 MCP Server，由 MCP
Server 去呼叫 OpenAI。

下面四個是主要的設定參數，每個都有對應的理由：workers 設 3 個，因為坐姿
推論吃 CPU，要多個 process 才能平行處理，但每個 worker 都要各自載入一份
模型，3 個合計大約 1 GB 記憶體，所以數量是由記憶體決定的；threads 設 8
條，因為 Physio Agent 要等 OpenAI 回應，可能要幾秒到幾十秒，用 thread
撐住這些等待中的請求，才不會一個 Agent 請求就卡死整個 worker；timeout
設 120 秒，必須大於 Agent 本身的 60 秒逾時，否則 Agent 還沒回完，worker
就被 Gunicorn 強制終止；max_requests 是讓 worker 定期重生、避免記憶體
洩漏，但重生要重新載入模型，門檻不能設太低，這點後面壓測會講到。這些
參數都可以從 .env 調整，不需要改程式碼。

────────────────────────────────────────
【Page 23：壓力測試方法與 KPI 定義】
────────────────────────────────────────
為了量化換伺服器前後的差異，我寫了一支壓力測試腳本 load_test.py，可以
重複執行，結果存成 JSON，部署前後用同一支腳本、同一台機器測，數字才能
直接對照。

測試的端點有三個，由輕到重：health 只驗證資料庫連線，用來量伺服器本身的
上限；posture/history 包含 Token 驗證、資料庫查詢和序列化，代表前端一般
的查詢；最重要的是 POST /api/posture，椅子每次上傳感測資料都會打這支
API，裡面包含格式檢查、TensorFlow 推論和資料庫寫入，是最重也最關鍵的
請求。

測試方式是封閉迴圈：N 個虛擬使用者持續送請求，前一個回來才送下一個。
併發數分別測 1、10、30、50，每組 15 秒，三個端點乘四種併發乘三種伺服器，
總共 36 組。

KPI 有三個：QPS 是每秒成功完成的請求數；p95 延遲是 95% 的請求都在這個
時間內完成；錯誤率不只算失敗比例，還會依 HTTP 狀態碼和連線例外的類型
分類統計，後面抓到的問題就是靠這個分類追出來的。

/api/agent 刻意不測，因為它的瓶頸在外部的 OpenAI，不在我們的伺服器，
而且每呼叫一次都會產生費用。

────────────────────────────────────────
【Page 24：測試結果：坐姿預測 POST /api/posture】
────────────────────────────────────────
這頁是最關鍵的坐姿預測結果，比較了三種伺服器：原本的 runserver、ASGI
架構的 Uvicorn，以及最後採用的 Gunicorn。

左邊是吞吐量，越高越好。runserver 在 10 個併發之後就卡在每秒 33 個請求
左右，再多人也只是排隊；Gunicorn 三個 process 平行推論，可以到每秒 70
幾個。右邊是 p95 延遲，越低越好，可以看到 runserver 隨著人數增加延遲
一路往上，50 人同時上傳時 95% 的請求要等到 2.45 秒；Gunicorn 只要 0.92
秒。

總結下面三個數字：50 個併發下吞吐量從 32.9 提升到 71.0 QPS，大約 2.2 倍；
p95 延遲從 2.45 秒降到 0.92 秒；三種伺服器在所有併發等級的錯誤率都是 0%。
另外補充，這個改善在我開啟資料庫持久連線之前就已經達到，所以可以單獨
歸功於 Gunicorn 的多 process 架構。

────────────────────────────────────────
【Page 25：測試結果：輕量請求與選型結論】
────────────────────────────────────────
左邊是另外兩個比較輕量的端點，Gunicorn 在 health 和 history 的每個併發
等級也都是最高的。這邊要說明一下，這張表的提升同時包含了「換成
Gunicorn」和「資料庫持久連線」兩項改動，持久連線的部分下一頁會講；上一頁
坐姿預測的提升則是單獨來自 Gunicorn。

原本排程是要評估 WSGI 跟 ASGI 兩種架構，最後用實測數據決定採用 Gunicorn，
理由有三個：第一，實測三個端點、所有併發等級，QPS 和延遲都優於另外兩者；
第二，我們的 API 全部是同步寫法，在 ASGI 底下 Django 會把同步的 view
排在同一條執行緒上執行，反而失去平行處理的能力；第三，Django 官方文件
註明 ASGI 需要關閉資料庫持久連線，我實測開啟的話，Uvicorn 的坐姿預測
錯誤率會到 76% 到 95%。

────────────────────────────────────────
【Page 26：壓力測試抓出的問題與修正】
────────────────────────────────────────
壓力測試除了量數字，也在正式上線前抓出三個問題。因為錯誤有依類型分類
統計，才能從「有失敗」一路追到真正的原因。

第一個最重要，是資料庫連線埠耗盡。換成 Gunicorn 之後，health 開始回 503，
錯誤率最高到 81%，history 也出現 500。追查發現 Django 預設每個請求都新開
一條資料庫連線，用完就關，但關掉的連線還會佔住本機的連線埠大約 60 秒；
Gunicorn 變快之後每秒有好幾百個請求，就把連線埠用光了，錯誤訊息是
「Cannot assign requested address」。原本的 runserver 速度慢，所以從來沒有
踩到。修正方式是開啟資料庫持久連線，讓每條 thread 重用連線 60 秒，並在
重用前先檢查連線是否還活著，修正後錯誤率降到 0%。

第二個是 worker 頻繁重生。一開始 max_requests 設 2000，整輪測試中 worker
被重生了大約 20 次，每次都要重新載入 TensorFlow 模型，重生瞬間的請求就會
失敗，吞吐量也忽高忽低。門檻調到 50000 並讓各 worker 隨機錯開之後，測試
期間就沒有再重生。

第三個是模型冷啟動。原本模型是在第一次用到時才載入，所以每個 worker 收到
的第一個請求都要多等好幾秒。改成 worker 開機時就預先載入，把等待的成本
移到開機階段，使用者就不會遇到。

────────────────────────────────────────
【Page 27：強化：服務卡住時自動重啟】
────────────────────────────────────────
這頁處理的是「程式沒有當掉、但其實卡住了」的情況。一般 Docker 的健康檢查
只會把容器標記成 unhealthy，並不會重啟它；而 restart policy 只有在程式真的
結束時才會生效。所以程式卡住但沒當掉的時候，需要額外的機制讓它結束。

左邊是重啟流程：第一步，healthcheck.py 每 30 秒檢查一次，django 跟 mcp
用 HTTP 請求，mqtt-subscriber 檢查心跳檔案；第二步，連續 3 次失敗才判定
卡住，而且啟動後 90 秒內不計，因為模型還在載入；第三步，強制終止主程式，
這裡要設定 init: true，讓 tini 當容器的 PID 1，否則主程式自己就是 PID 1，
從容器內部是砍不掉的；第四步，容器結束之後，由 restart policy 自動重啟。

右邊是實測結果。我對三個容器裡的程式送 SIGSTOP 訊號，模擬程式卡死：django
和 mcp 大約 90 秒後自動重啟，mqtt-subscriber 因為心跳逾時要 120 秒，加上
3 次檢查，大約 3.5 分鐘重啟。三個服務都只重啟一次就恢復正常，API 也正常
回應。

另外兩個設計細節：mcp 的檢查從 TCP 連線改成 HTTP 請求，因為程式卡住的時候
作業系統仍然會完成 TCP 連線，用 TCP 檢查偵測不到；django 如果回 503，代表
伺服器活著、只是資料庫有問題，這種情況只標記 unhealthy、不重啟，因為重啟
django 也修不好資料庫。

────────────────────────────────────────
【Page 28：部署驗證時發現的既有問題與資安修正】
────────────────────────────────────────
最後這頁是部署驗證過程中發現的問題，全部都已經部署到遠端正式後端，並且
透過 ngrok 外部網址驗證過。

上排三個是既有的功能問題：第一，MQTT 服務在閒置時被誤判為異常，因為心跳
只在收到訊息時更新，椅子沒人坐超過 120 秒就被判定不健康，改成用 MQTT
keepalive 的回應來更新心跳，實測閒置 3.5 分鐘仍然正常；第二，Agent 的錯誤
訊息沒有生效，真正的錯誤被包在 ExceptionGroup 裡面，原本的中文錯誤訊息
比對不到，改成把裡面的子例外取出來比對，實測停掉 MCP Server 時會回傳正確
的中文提示；第三，知識庫查詢失敗，因為舊的資料還留著 Gemini 時期建的索引，
是 3072 維，跟現在 OpenAI 的 1536 維不符，改成載入時先比對維度，不符就
自動重建，已經確認能查到正確的文獻。

下排三個是資安修正：第一，DEBUG 原本寫死開啟，任何人連到 ngrok 網址、只要
觸發錯誤，就看得到完整的路由表跟程式路徑，現在改由 .env 控制、預設關閉，
錯誤頁只會顯示 Not Found；第二，Django 的 SECRET_KEY 是建專案時自動產生、
直接寫在 settings.py 裡，隨著程式碼上傳到公開的 GitHub。這邊要說明，
OpenAI 這些需要付費的 API 金鑰一直都放在 .env，從來沒有上傳過；外洩的只有
Django 內部用來簽章的金鑰，現在已經作廢換新，改從 .env 讀取，正式環境沒有
設定就直接拒絕啟動；第三，透過 ngrok 登入後台時出現 403，因為 ngrok 對外是
https、轉進後端是 http，CSRF 的來源檢查對不上，設定 CSRF_TRUSTED_ORIGINS
之後就能正常登入，而其他網站送來的請求仍然會被擋下。
